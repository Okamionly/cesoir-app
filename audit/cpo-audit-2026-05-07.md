## Analyse Narrative (~600 mots)

### Value Prop : "ce soir" est un vrai moat — mais personne ne le sait encore

La landing "Personne ne dîne seul ce soir à Montpellier" est la meilleure phrase de la stack entière. Elle résout le problème de Tinder (pool trop large, pas de temporalité), de Hinge (trop lent, pas de géo immediate), de Happn (proximité mais pas d'intention déclarée). Le hook "ce soir" force une intention que les autres apps diluent sur des semaines de swipe. C'est réel.

Le problème : 24 migrations Supabase non pushées signifient que la quasi-totalité des features Wave 16 et 17 qui donnent corps à cette promesse (broadcast "je suis dispo ce soir", vibes, voice intro, moments) sont dormantes en prod. Un visiteur voit une v1. Le builder a une v3. Ce gap est le seul vrai urgence.

### Finding 1 — /profile : chantier de construction ouvert au public

Le /profile est le meilleur exemple de feature creep dans le produit. En scrollant, un utilisateur rencontre dans l'ordre : avatar animé + halo respirant + badge travel passport + bio 2-line + bouton AI bio + pill "Disponible ce soir" + pill mode actif + AvailabilityBroadcast + 4 badges + voice intro recorder + bouton "Modifier le profil" + MasteryStrip + VibePicker + 6 tonight chips + 3 prompts Hinge-style + nav découvrir + nav réglages + logout.

Ce n'est pas un profil. C'est un formulaire de 14 sections. Hinge met 3 prompts et 6 photos sur un profil consulté. CeSoir met 14 zones d'interaction dont 4 requièrent des décisions actives (vibe, chips, broadcast, prompts). Un utilisateur à J+1 en état d'"app anxiety" (ie: n'a pas encore eu de match) va quitter cette page sans l'avoir remplie.

Recommandation : séparer /profile (vue que les autres voient = read-only) de /profile/edit (configuration). Le hero doit se réduire à avatar + nom + toggle "Dispo ce soir". Tout le reste va dans edit.

### Finding 2 — Wave 17 : 10 features pour 0 utilisateurs

Le principe de base du développement produit post-PMF est l'inverse de l'ordre suivi ici. On valide un core loop (swipe → match → chat → IRL) avec 100 personnes, on mesure le drop-off par étape, et on build la feature qui réduit le plus gros drop-off. Crystal ball, QR check-ins, passport, saved searches ont été construits avant que le core loop soit validé une seule fois avec un vrai utilisateur montpelliérain.

Le code est bon — la codebase est saine (7/10 Round 3). Le problème est l'ordre des priorités. La recommandation ROADMAP de ne "pas lancer une autre vague de 20 features avant 500 users" est exacte mais elle arrive après le fait.

### Finding 3 — /chat : le meilleur écran, sous-distribué

Le /chat [id] est techniquement le plus complet et le plus cohérent : SparkTimer (urgence), IcebreakerSuggestions (AI), AIWingman (fallback), WeMetFeedback (loop post-date), IRLConfirm (conversion IRL), VoiceMessageRecorder (différenciateur). C'est l'écran qui représente le mieux la vision produit "ce soir, pour de vrai".

Problème : l'utilisateur n'y arrive que s'il a eu un match, et les matchs n'existent que si la géolocalisation fonctionne, et la géolocalisation ne renvoie des profils que si les migrations sont pushées. Le chat est au bout d'un funnel dont les 3 premières étapes sont bloquées.

### 3 Recommandations prioritaires

1. **Cette semaine :** `supabase db push` + 7 env vars Vercel. Sans ça, tout le reste est théorique.
2. **Semaine 2 :** /profile split en read / edit. Réduction du cognitive overload avant tout utilisateur externe.
3. **Semaine 3 :** Câbler le VoiceIntro upload (TODO dans profile/page.tsx ligne 473) + fallback statique IcebreakerSuggestions sans ANTHROPIC_API_KEY.

## Notifications Strategy

Triggers câblés (mig 033, dormants) :
- **Match** → instant push. A/B tester copy : "Tu as un nouveau match ce soir" vs "[Prénom] t'a liké en mode Solo Diner"
- **Message** → instant push. Limite : max 1 push/heure si multiple messages (anti-spam)
- **Last Call 19h45** → cron daily. Copy : "Il reste 2h pour matcher ce soir"
- **Rappel 24h inactivité** → "X nouveaux profils dans ta zone depuis hier"
- **Streak reminder 23h45** → "Ta streak de X jours est en jeu"

Cadence sustainable sans churn : 2 push max/jour. Au-delà, opt-out rate explose (benchmark dating apps : >3 push/jour = +40% opt-out). La "Last Call 19h45" est la plus précieuse car elle est alignée avec le use case core. C'est le seul push qui doit être envoyé même à un user actif ce jour-là.

## Onboarding Redesign : 4-step tooltip vs nécessaire

Le tooltip 4 étapes sur /browse (data-tour="swipe-deck", data-tour="like-button") est vu dans le code browse. C'est minimal et c'est bien. Le problème n'est pas l'onboarding browse — c'est le funnel en amont :

```
Landing → Signup → [GAP] → Browse → First Swipe → First Match → First Chat → IRL
                     ^
           Ici l'utilisateur ne sait pas quoi faire
```

Le "GAP" entre signup et premier swipe n'a pas d'écran de contexte. L'utilisateur ne sait pas que :
- Il doit activer un mode (Solo Diner, etc.)
- Il doit activer la géolocalisation
- Les profils se renouvellent chaque soir

Recommandation : un seul écran post-signup (pas un carousel de 5) : "Tu es à Montpellier ce soir. Quel est ton plan ?" → picker de mode → /browse avec le mode pré-sélectionné. Le tooltip 4 étapes peut rester comme aide contextuelle.
