# CTO Audit — CeSoir App
**Date :** 2026-05-07 | **Auditeur :** CTO Agent | **Scope :** Wave 17, 48 migrations

---

## Resume executif (500 mots)

CeSoir est une application de rencontres IRL-first construite sur Next.js 16 App Router + React 19 + TypeScript strict + Tailwind v4 + Supabase. Le codebase est techniquement mature pour un projet solo : CI/CD en place (Lint + Types + Vitest + Build + db-types-drift + Playwright + gitleaks), Sentry integre, CSP header configure, RLS actif sur toutes les tables, rate-limiting Upstash.

**Stack resumee :** Frontend Next.js 16.2.3 / React 19.2.4. Backend Supabase (Auth + Postgres + PostGIS + pg_net + RLS). Infra Vercel (Hobby, 2 crons). CI GitHub Actions (2 workflows). Testing Vitest (15 fichiers unit/integration) + Playwright E2E (3 specs). Monitoring Sentry + PostHog.

**3 findings critiques :**

**1. `compute_ghost_score(UUID)` expose l'activite privee de n'importe quel utilisateur.** La fonction est `SECURITY DEFINER`, accepte un `uid` arbitraire en parametre, et est `GRANT EXECUTE` a `authenticated`. N'importe quel utilisateur connecte peut appeler `SELECT public.compute_ghost_score('<victim_uuid>')` et obtenir des meta-comportementales sensibles (nombre de conversations sans reponse, annulations tardives, matches silencieux) d'une victime tierce. La fonction ne contient aucune verification que le caller est bien l'uid cible. C'est une fuite d'informations comportementales cross-user.

**2. TensorFlow.js + nsfwjs + @vladmandic/face-api dans le bundle client.** Ces trois packages (`@tensorflow/tfjs` 4.22, `nsfwjs` 4.2, `@vladmandic/face-api` 1.7) sont des dependances `dependencies` (pas `devDependencies`), donc inclus dans le bundle de production. TensorFlow.js seul ajoute environ 2-4 MB gzip. Ils sont utilises uniquement cote client dans `src/lib/nsfw.ts` et `SelfieVerification.tsx`. Sans dynamic import avec `ssr: false` et `lazy()`, ils gonflent le First Load JS, degradant le TTI — critique pour une PWA mobile.

**3. 47 migrations sans squash + 24 migrations non poussees en production.** La ROADMAP-Q2-Q4-2026.md confirme explicitement que Wave 16 et Wave 17 sont "DORMANTES" en DB production. Crystal Ball, Voice Messages, Moments, Passport, Anti-ghost decay, Mastery Tiers — toutes ces features sont shippees dans le code Next.js mais la DB prod ne les connait pas encore. Chaque deploy Vercel execute du code qui appelle des RPCs inexistantes (`crystal_ball_matches`, `compute_ghost_score`, `apply_ghost_decay`), generant des erreurs 500 silencieuses.

**3 recommandations :**

1. **Patcher `compute_ghost_score` immediatement** : ajouter `IF uid <> auth.uid() THEN RAISE EXCEPTION 'forbidden'` en debut de fonction, ou retirer le GRANT `authenticated` et passer par une API route server-side.

2. **Dynamic imports pour le ML bundle** : deplacer TensorFlow.js / nsfwjs / face-api en `dynamic(() => import(...), { ssr: false })` + lazy loading conditionnel au seul contexte photo-upload/selfie. Gain estimé : -3 MB First Load JS.

3. **`supabase db push` cette semaine** : les 24 migrations en attente bloquent 100% des features Wave 16+17. C'est la P0 operationnelle avant tout nouveau code.

## Findings

### P0 — Critiques (bloquer deploy ou patcher dans les 48h)

#### P0-1 — Fuite comportementale via `compute_ghost_score`
- **Area :** Security
- **Observation :** `supabase/migrations/045_anti_ghost_decay.sql` ligne 392 : `GRANT EXECUTE ON FUNCTION public.compute_ghost_score(UUID) TO authenticated`. La fonction accepte un `uid UUID` arbitraire, n'execute aucun check `IF uid <> auth.uid()`, et retourne le score de ghosting (0-3) d'un utilisateur tiers. Une requete `SELECT public.compute_ghost_score('victim-uuid')` cote client retourne des informations comportementales privees : nombre de conversations sans reponse, annulations tardives de flash_plans, nombre de matches silencieux.
- **Recommandation :** Ajouter en debut de fonction : `IF uid <> (SELECT auth.uid()) THEN RAISE EXCEPTION 'forbidden_cross_user' USING ERRCODE = '42501'; END IF;`. Ou retirer le GRANT authenticated et exposer uniquement via API route server-side avec verification d'identite.
- **Severity :** critical

#### P0-2 — 24 migrations non deployees en production
- **Area :** Reliability
- **Observation :** ROADMAP-Q2-Q4-2026.md confirme : "Wave 16 + 17 sont DORMANTES. Sans push : Crystal Ball, Vibes, Streaks, Voice messages, Moments, Passport, AI features → invisibles". Le code Next.js appelle des RPCs (`crystal_ball_matches`, `apply_ghost_decay`, `process_qr_scan`, `generate_daily_crystal_ball`) qui n'existent pas en DB prod. Chaque appel genere une erreur 500 silencieuse.
- **Recommandation :** `supabase db push` + validation des 7 env vars manquantes (VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY, VAPID_SUBJECT, ANTHROPIC_API_KEY, CRON_SECRET, PUSH_INTERNAL_SECRET, NEXT_PUBLIC_SUPABASE_URL en DB setting).
- **Severity :** critical

#### P0-3 — ML bundle non lazy-loaded (TTI mobile degrade)
- **Area :** Scalability / Performance
- **Observation :** `@tensorflow/tfjs` (4.22), `nsfwjs` (4.2), `@vladmandic/face-api` (1.7) sont en `dependencies` (pas `devDependencies`) et charges de maniere synchrone. `src/lib/nsfw.ts` utilise `loadModel()` lazy en interne mais l'import du module lui-meme est top-level. Sur une PWA mobile 3G, le First Load JS est penalise de ~3-4 MB gzip. `SelfieVerification.tsx` et `moderate-photo/route.ts` sont les seuls consommateurs.
- **Recommandation :** Convertir en `next/dynamic(() => import('@/lib/nsfw'), { ssr: false })` uniquement dans `PhotoUpload.tsx` / `SelfieVerification.tsx`. La route `/api/moderate-photo` est server-side et peut garder l'import statique. Verifier avec `next build --analyze` (bundle analyzer) l'impact reel.
- **Severity :** critical

### P1 — Importants (sprint suivant)

#### P1-1 — `apply_ghost_decay` : boucle O(N) sans pagination
- **Area :** Scalability
- **Observation :** `supabase/migrations/045_anti_ghost_decay.sql` ligne 272+ : la fonction boucle sur `SELECT u.id FROM auth.users JOIN profiles` sans LIMIT. A 10 000 utilisateurs, chaque appel cron execute 10 000 iterations sequentielles avec 4-5 sous-requetes par iteration dans une seule transaction Postgres. Timeout Vercel Hobby cron = 5 minutes, Pro = indefini. Avec `maxDuration = 300` dans le route handler, on risque le timeout avant completion sur une base utilisateurs reelle.
- **Recommandation :** Ajouter un mecanisme de pagination par batch (cursor-based sur `u.id`) avec un parametre `batch_size INT DEFAULT 500`. Ou passer a une approche event-driven (trigger sur update conversations/flash_plans) plutot qu'un scan global.
- **Severity :** important

#### P1-2 — `send_push_notification` : URL de destination configurable par DB setting
- **Area :** Security (SSRF)
- **Observation :** `supabase/migrations/033_push_triggers.sql` : `send_url TEXT := current_setting('app.push_send_url', true)`. Le trigger DB construit l'URL cible depuis un setting Postgres (`app.push_send_url`). Si un attaquant obtient un acces DB (pas RLS — acces SQL direct via compromission service_role ou credentials DB), il peut modifier ce setting pour rediriger les POSTs pg_net vers une URL arbitraire (SSRF interne, metadata cloud, etc.). Le risque est conditionnel a une compromission DB prealable mais le vecteur est documentable.
- **Recommandation :** Valider que `send_url` commence par `https://cesoir.app/` ou l'URL de domaine attendue avant le `net.http_post`. Ajouter un CHECK dans la fonction : `IF send_url NOT LIKE 'https://cesoir.%' THEN RAISE EXCEPTION 'invalid_push_url'; END IF;`.
- **Severity :** important

#### P1-3 — Trilateration : protection correcte mais fragile sur l'iteration
- **Area :** Security
- **Observation :** Migrations 024 (grid-snap 500m) + 026 (distance roundee au 1 km) implementent la protection SEC-002 correctement. Migration 040 (`travel_passport`) confirme : "The 500m grid-snap and 1 km distance rounding from migrations 024/026 (SEC-001/SEC-002) ARE STILL APPLIED". La protection est correcte aujourd'hui. Le risque est structurel : chaque rewrite de `nearby_profiles` (4 rewrites sur 048 migrations) doit manuellement re-appliquer les deux guards. Un refactor oublie peut reintroduire la vulnerabilite.
- **Recommandation :** Extraire la logique de snap et de distance-round dans des fonctions SQL dedie (`snap_to_grid(lat, lng)` et `round_distance_km(dist)`) pour que chaque rewrite de `nearby_profiles` compose les primitives au lieu de les re-implementer. Ajouter un test Vitest qui appelle l'RPC avec deux coords connues et verifie que `distance_km` est toujours un entier et que `lat_rough`/`lng_rough` sont quantises a 0.005 deg.
- **Severity :** important

#### P1-4 — Coverage test insuffisante pour la surface de code
- **Area :** Code Quality
- **Observation :** 15 fichiers de tests Vitest pour ~378 fichiers TypeScript. 3 specs E2E Playwright (login, chat-send, events-rsvp). Aucun test sur les paths critiques : `process_qr_scan` RPC, `apply_ghost_decay`, `crystal_ball_guard_update`, routes `/api/swipe`, `/api/match/confirm-irl`. Le rapport de coverage n'est pas genere en CI (pas de `vitest run --coverage` dans `ci.yml`).
- **Recommandation :** Ajouter `npm run test:coverage` dans le job CI avec un seuil minimum (`--coverage-threshold lines:60`). Priorite tests : `src/lib/matching.ts` (algorithme core), `src/app/api/swipe/route.ts`, `src/lib/rate-limit.ts` (deja teste — bon). Ajouter 2 E2E : swipe-to-match flow + QR checkin flow.
- **Severity :** important

#### P1-5 — CSP `unsafe-inline` sur `script-src`
- **Area :** Security
- **Observation :** `next.config.ts` ligne 50 : `"script-src 'self' 'unsafe-inline'"` en production. Le commentaire reconnaît que c'est temporaire ("Next still ships an inline script for initial state hydration"). `unsafe-inline` annule la protection XSS du CSP pour les scripts. Next.js 16 supporte les nonces CSP via `generateBuildId` + `nonce` header.
- **Recommandation :** Implementer les nonces CSP Next.js 16 (middleware qui injecte un nonce par requete + `headers()` dans `next.config`). Retirer `unsafe-inline` de `script-src`. Effort : 1 journee de migration.
- **Severity :** important

### P2 — Ameliorations (Q3 2026)

#### P2-1 — 47 migrations sans squash
- **Area :** Tech Debt
- **Observation :** 47 fichiers SQL individuels dont plusieurs reecrivent la meme fonction (`nearby_profiles` : migrations 024, 026, 030, 040 — 4 rewrites). Le cold start d'un nouveau developer ou d'une Supabase Branch rejoue 47 migrations en sequence. Le schema resultant est correct mais l'historique est bruit.
- **Recommandation :** Creer un `supabase/migrations/000_squash_baseline.sql` qui capture l'etat actuel (`pg_dump --schema-only`) et archiver les migrations 001-047 dans `supabase/migrations/archive/`. A faire apres le push des 24 migrations manquantes, pas avant. Cible : Q3 apres premier milestone 500 users.
- **Severity :** nice-to-have

#### P2-2 — Duplication logique nearby_profiles entre browse, map, et matching.ts
- **Area :** Code Quality
- **Observation :** `src/lib/useProfiles.ts` (119 lignes) et `src/lib/matching.ts` appellent tous les deux directement `.rpc("nearby_profiles", {...})` avec des parametres similaires. `src/app/(app)/map/page.tsx` (1116 lignes) contient sa propre logique de fetch. Pas de hook partage central pour la pagination/deduplication.
- **Recommandation :** Consolider dans `useProfiles.ts` qui devient la source unique. `matching.ts` et `/map/page.tsx` importent le hook au lieu d'appeler directement le RPC. Reduire `map/page.tsx` de 1116 a <400 lignes en extractant les composants `MapPin`, `ClusterMarker`, `ProfileBottomSheet`.
- **Severity :** nice-to-have

#### P2-3 — Avatar URL legacy TODO non resolu
- **Area :** Tech Debt
- **Observation :** `src/lib/storage.ts` (ligne 28-32) : "TODO (post-028 rollout): Audit `profiles.avatar_url` rows for the legacy `/object/public/` prefix [...] OG previews fall back to ui-avatars.com." Le bucket a ete passe en PRIVATE dans mig 028 mais les URLs en DB n'ont pas ete backfillees. Les OG image cards (partage profil) affichent un avatar generique ui-avatars.com au lieu de la vraie photo.
- **Recommandation :** Script de migration one-shot : `UPDATE profiles SET avatar_url = regexp_replace(avatar_url, '.*/avatars/', '') WHERE avatar_url LIKE '%/object/public/avatars/%'`. Puis mettre a jour `opengraph-image.tsx` pour utiliser `createSignedUrl`.
- **Severity :** nice-to-have

#### P2-4 — Vercel Hobby : crons limites a 2, maxDuration 300s
- **Area :** Scalability
- **Observation :** `vercel.json` a 2 crons declares (`/api/push/last-call` + `/api/cron/anti-ghost`). Le plan Hobby Vercel limite a 2 crons ET impose une execution max de 300s. `crystal-ball`, `nightly-vibe`, et d'autres crons Wave 17 n'ont pas encore de schedule configure. Passer Pro est necessaire avant 500+ users (crons illimites, 800s max duration).
- **Recommandation :** Passer Vercel Pro quand premiers utilisateurs payants (deja note dans `alert_vercel_pro_upgrade.md`). En attendant, combiner les crons Wave 17 dans un seul endpoint `/api/cron/daily` qui orchestre les appels dans une sequence.
- **Severity :** nice-to-have

Creer un environnement Supabase Branch dedie pour les E2E CI. Premier recrutement recommande : un second developer full-stack a partir de 1000 users actifs.
